## 2026-09-12 - Keyboard Shortcut and Modal Close Accessibility
**Learning:** We realized that global keyboard shortcuts in the dashboard were hijacking inputs for users trying to use forms (specifically in elements with `isContentEditable` set). Additionally, drawer/modal components were missing standard Escape key listeners, forcing users to click close buttons or the backdrop, thus limiting keyboard navigation.
**Action:** Always verify `document.activeElement?.isContentEditable` alongside input and textarea tags when writing custom keyboard shortcut hooks. Furthermore, all overlay menus must pair with an `Escape` key close listener to support non-mouse accessibility.
## 2024-09-20 - Accessible Disabled Buttons & Strict DOM Budgets
**Learning:** Wrapping disabled buttons in a `div` with a `title` and `tabIndex={0}` is crucial for accessibility, as it allows both keyboard and screen reader users to understand *why* an action is disabled (since disabled elements natively suppress focus and pointer events). However, in high-performance React frontends (like this project's Next.js app), doing so may conflict with strict DOM node budget assertions (e.g., `make ui-test` checking exact node counts). Adding `focus-visible` outlines or replacing `transition-all` with `transition-colors` to prevent layout thrashing also requires coordinating with strict class regex tests.
**Action:** When making structural accessibility improvements (like wrapper divs for disabled states) or transition changes in strict DOM budget environments, always verify node counts and adjust baseline tests concurrently to ensure optimizations pass CI without breaking accessibility features.
